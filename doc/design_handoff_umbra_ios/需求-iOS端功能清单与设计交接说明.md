# Umbra iOS 端 · 功能清单与设计交接说明

> **读者**：ClaudeDesign（要按这份文档重做 iOS 端的样式与信息架构）
> **参照物**：Umbra PC 端（Electron + React，已实现）、Umbra 服务端（FastAPI）、现有 UmbraiOS（SwiftUI，21 个源文件）
> **平台范围**：**只写 iPhone 竖屏**。iPad 与横屏这一版不做，也不必留适配位。
> **写于** 2026-07-30

---

## 〇、先讲清楚这个东西是什么

Umbra 是一个「AI 秘书 + 一台或多台执行设备」的系统。

- **秘书**跑在服务端，是唯一的对话对象。你跟它说话，它负责理解、追问、拆活、派活。
- **执行设备**是装了 Umbra 客户端的机器。PC 端既是客户端也是执行设备 —— 秘书派下来的活（写代码、跑脚本、操作软件）在它上面真跑。
- **服务端是唯一真相源**。聊天记录、任务、灵感、工作区、常用语、保险箱密文，全部存在服务端，多端共享。

**iOS 端在这套东西里的角色不是「PC 的缩小版」，而是「随身的那一半」。**

PC 端的重心是**干活**：写代码、跑工作流、按快捷键唤起搜索框、截图标注、翻剪贴板历史。这些都要求你坐在电脑前、双手在键盘上。

iPhone 的重心是**接头与随手记**：

| 手机比电脑强的 | 为什么 |
|---|---|
| 收到"有事找你" | 推送。任务卡住了、秘书要问一句、提醒到点了 —— 电脑合着盖，手机在兜里 |
| 随手记一条 | 灵感、提醒。想到就记，不用开机 |
| 随手查一下 | 保险箱密码、任务跑到哪了、常用语 |
| 随手答一句 | 问答卡、执行前确认。一句话就能让卡住的活继续跑 |

**所以设计基调是：iOS 端要像一个"随时能接头的秘书通道"，而不是一个功能列表。** 凡是"要坐下来慢慢配"的东西（能力配置、工作流编排、快捷键），都往深处放；凡是"有事找你 / 你随手一句"的东西，都放在一级。

**视觉基调延续 PC 端**：暖白/暖黑底 + 单一橙色主色（`#E8590C`），克制的线性图标，语义色只有四种（绿=成功、橙=进行中、黄=要人处理、红=失败）。不要引入第二个主色，不要用彩色 emoji 当图标 —— PC 端为此专门返工过一次（emoji 跨平台字形与基线对不齐）。

## 一、现状盘点

### 1.1 PC 端有哪九个页面

| PC 页面 | 职责 | iOS 该怎么办 |
|---|---|---|
| 聊天 | 跟秘书对话 + 跟每台设备单独对话 | **一级，必做** |
| 任务 | 秘书派下去的活，看进度/重试/停止/删除 | **一级，必做** |
| 工作区 | AI 写文件的落地目录 | 二级，只读为主 |
| 灵感 | 随手记的点子，秘书自动补标题与标签 | **一级，必做** |
| 能力 | 本机装了什么程序、AI 能用什么技能 | 二级，只读 |
| 实时操作 | AI 正在操作电脑时的实况与动作历史 | **不做**（见第四章） |
| 工具 | 快捷入口 / 剪贴板 / 截图 / 工作流 / 常用语 / 保险箱 | **拆开处理**（见第四章） |
| 日志 | 设备引擎日志，排障用 | 三级，塞在设备详情里 |
| 设置 | 连接、设备、权限、全局快捷键 | 二级 |

### 1.2 iOS 端现在有什么

现有五个 tab：**聊天 / 任务 / 灵感 / 能力 / 我**，密码保险箱挂在「我」里的一个 NavigationLink 上。

已经能用的：

- 聊天：WebSocket 连接、流式回复（`delta`）、工具轨迹（`tool_call` / `tool_result`）、执行前确认卡（`confirm_request` / `confirm_resolved`）、设备消息（`device_message`）、设备在线状态（`device_presence`）、历史分页、TTS 朗读
- 任务：列表、详情、停止
- 灵感：列表、增删改
- 能力：只读列表
- 我：服务端地址 / Token、computer-use 开关、自动批准、语言、深色模式、关于
- 保险箱：已有一份独立的设计交接（`UmbraiOS/doc/根据文件设计样式功能/uploads/密码保险箱-样式规范(设计交接).md`），且底层加密已经为跨端复现做过准备（主密码派生统一走 PBKDF2-SHA256，就是为了 iOS 原生能算出同样的密钥）

### 1.3 已经查证的缺口

这几条是逐个对过代码的，不是印象：

1. **问答卡完全没接**。服务端会通过 `/ws/chat` 广播 `type: "question_card"`，iOS 的 `ChatWebSocket` / `ChatViewModel` 里搜不到这个字符串。后果是：秘书派活前想问一句"做在微信小程序还是支付宝小程序"，手机上什么都不会出现，对话就那么停住了 —— 用户完全不知道在等自己。**这是本次最该补的一个洞。**
2. **提醒与定时任务整套都没有**。服务端也没有，设计已落在 `doc/提醒与定时任务-设计与待办.md`，标注为"未开工"。
3. **常用语、工作区、用户画像三块在 iOS 上完全缺席**，服务端接口都已就绪。
4. **任务详情缺了一多半**：验收清单、事件时间线、里程碑、自动补做轮次、重试、批量删除，PC 端都有，iOS 只有停止。
5. **灵感缺了筛选与排序**：PC 端有状态筛选、标签栏、三种排序、来源标签、"让 Umbra 去做这件事"（转任务）。
6. **「我」里有两条在 iPhone 上语义不成立**：`辅助功能` 开关被硬编码成常开，`computer-use` 总开关 —— 这两个是**执行设备**的属性，iPhone 不是执行设备，不能操作自己的屏幕。这两项要改成"查看 PC 设备的状态"，而不是本机开关。

## 二、信息架构方案

### 2.1 主推方案：聊天 / 提醒 / 任务 / 灵感 / 我

```
① 聊天        ② 提醒            ③ 任务          ④ 灵感        ⑤ 我
├ 联系人列表   ├ 待办 | 已完成   ├ 进行中|计划    ├ 列表        ├ 保险箱（大入口卡）
│ · 秘书       ├ 提醒详情        ├ 任务详情       ├ 灵感详情    ├ 常用语
│ · 各台设备   └ 新建/编辑提醒   └ 定时任务详情   └ 新建/编辑   ├ 工作区
├ 与秘书对话                                                    ├ 设备与能力
├ 与设备对话                                                    │ └ 设备详情 → 日志
└ 设备详情                                                      ├ 用户画像
                                                                └ 设置
```

**为什么这么排：**

- **提醒进一级**。提醒的全部价值在"人不在电脑前的时候把他叫住"，落点必然是手机推送。推送点开要直达详情，中间不能再垫一层 tab 内的分段控件。这是这一版新增的重头，藏起来等于没做。
- **能力从一级降到三级**。它是"这台 PC 装了 ffmpeg 没有、AI 能不能用它"这类配置信息，一年看两次。占着底部五分之一的位置不合理。
- **保险箱不占 tab，但要在「我」的顶部做一张显眼的大入口卡**，支持 Face ID 一下解锁。它的使用模式是"偶尔用，用的时候很急"，靠一张卡 + 生物解锁足够快，不值得一个常驻 tab。
- **定时任务放「任务」tab 的第二段**（`进行中 | 计划`），不单独立项。它和普通任务的产物是同一种东西（在某台机器上跑一次），只是触发方式从"秘书派"变成"到点自己跑"，语义连着。
- **工作区放「我」里**。它是任务的附属信息（AI 把文件写哪了），手机上主要是"点进去看一眼有哪些文件、复制个路径"，不是入口级功能。

### 2.2 备选 A：把保险箱提到一级

`聊天 / 任务 / 灵感 / 保险箱 / 我`，提醒改成「任务」tab 的一个分段（`提醒 | 进行中 | 计划`）。

- **好处**：保险箱一步可达。如果你的实际使用里查密码远比看提醒频繁，这个更顺手。
- **代价**：提醒的推送深链要跳到"任务 tab 的第一段"，比跳一个独立 tab 脆弱；而且"提醒"（给人看的）和"任务"（AI 干的）挤在一个 tab 里，语义是混的 —— 用户会问"我的提醒怎么在任务里"。

### 2.3 备选 B：做一个「收件箱」

`聊天 / 收件箱 / 灵感 / 保险箱 / 我`。收件箱聚合**所有需要我处理的事**：到点的提醒、待确认的任务（`awaiting_review`）、待答的问答卡、失败待重试的任务。

- **好处**：这是最贴合"随身秘书"这个定位的方案。手机端的核心价值就是"有事找我"，把它做成一个明确的地方，用户每天只需要看这一个红点。角标数字也终于有了唯一的落点。
- **代价**：概念是新造的，PC 端没有对应物，两端的信息架构会分叉（以后 PC 端要不要也加一个？）；而且"收件箱清空了之后这个 tab 是空的"，空态设计要花心思。风险比前两个方案高。
- **建议**：如果拿不定，先按主推方案做，把"收件箱"的聚合逻辑作为二期在**聊天 tab 顶部的一条横幅**试水（"有 2 件事等你处理 →"），验证它的价值再考虑升格。

**下面的逐屏详述按主推方案写。** 若最终选了备选，屏幕内容不变，只是入口层级换个位置。

### 3.1 聊天 · 联系人列表 ｜ 一期

**职责**：选一个对话对象。对象有两类 —— 秘书（一个）和执行设备（0~N 台）。

**数据源**：`GET /contacts`（联系人）、`GET /devices`（在线设备）、`GET /conversations`（各会话的最后一条消息与时间）、WS `device_presence`（上下线实时变更）

**布局（自上而下）**

1. 大标题「聊天」
2. 分组标题「联系人」（10.5pt，字重 600，字间距 .06em，`--faint`）
3. **秘书行**（固定第一，永不消失）
   - 48pt 圆形头像
   - 主行：`秘书` + 右侧时间
   - 副行：`你的 AI 秘书`（没有历史时）或最后一条消息的预览，单行省略
   - 未读圆点/数字角标
4. **设备行**（每台一行）
   - 48pt 圆角方形头像（区别于秘书的圆形，一眼分清人和机器）
   - 主行：设备名 + 右侧时间
   - 副行：最后一条消息预览，或 `还没有对话`
   - **在线状态点**：在线 `已连接`绿实心点；离线灰空心圈 + 副行右侧 `最后在线 {{time}}`
5. 空态（一台设备都没有）：一句话说明"在电脑上装好 Umbra 并连上同一个服务端，它就会出现在这里"

**交互**

- 点一行 → 进对应对话
- 左滑设备行 → `从联系人列表移除`（红色）。点了要二次确认：`把「{{name}}」从联系人列表移除？（它下次上线会重新出现，聊天记录不会删除）`。走 `DELETE /devices/{device_id}`
- 下拉刷新
- 秘书行**不可左滑**，没有移除语义

**状态**：顶部要有一条连接状态条 —— `已连接` / `连接中…` / `未连接`。未连接时用警示黄，且**不要禁用输入框**（PC 端的做法是允许输入但发送后提示 `未连接到服务端，消息未发出。请检查设置里的服务端地址。`，iOS 沿用）

### 3.2 聊天 · 与秘书对话 ｜ 一期

**职责**：主对话。这是整个 App 使用频率最高的一屏，值得花最多的设计力气。

**数据源**：WS `/ws/chat`（收发）、`GET /history?conversation=assistant&limit=20&before_id=`（分页）、`POST /history/clear`、`POST /files/upload`（图片）

**布局**

1. 导航栏：标题 `秘书`，右侧 `⋯` 菜单
2. 消息流（倒序加载，顶部 `加载更早消息…`）
3. 底部输入区：模式选择器 + 输入框 + 附件 + 发送

**消息气泡**

- 用户消息：右对齐，`--user-bubble` 底色
- 秘书消息：左对齐，`--card` 底色 + 1px `--border`
- 支持 Markdown（PC 端有 `markdown.ts`，iOS 要对齐：粗体、行内码、代码块、列表、链接）
- 代码块右上角一个复制按钮
- 图片消息：圆角缩略图，点开全屏查看器（缩放/保存）
- 流式中：末尾一个跳动的光标或 `思考中…`
- 出错：`出错了` + 红色边框

**六种特殊卡片 —— 这是这一屏的重点，PC 端全都有，iOS 缺三种**

| # | 卡片 | 触发 | 内容与交互 | iOS 现状 |
|---|---|---|---|---|
| 1 | **工具轨迹** | `tool_call` / `tool_result` | 折叠条：`工具轨迹 · {{count}} 步`。点开逐步展开，每步是"工具名 + 参数摘要 + 结果摘要" | 已有 |
| 2 | **执行前确认** | `confirm_request` | 标题 `需要执行前确认` + 要做什么。三个按钮：`批准` / `总是允许` / `拒绝`。答完就地变成 `已批准，执行中…` 或 `已拒绝`。发 `job_confirm_response` | 已有 |
| 3 | **问答卡** | `question_card` | **见下方专节，必做** | ❌ **完全没有** |
| 4 | **任务进度卡** | `task_update` | 一张会**原地更新**的卡：任务目标 + 状态徽标 + 进度条（`overall` 是 0~1 的小数）+ 当前事件的一句话（`message`）。同一个 `task_id` 只有一张卡，不要每来一条就追加一条消息 | ❌ 缺 |
| 5 | **任务完成态** | `task_update` 里 `status` 变成 `done` / `failed` | 同一张卡变成完成态：绿勾 + `任务完成` + `查看结果` 按钮 → 跳任务详情的"生成结果"区；失败则红叉 + `重试任务` | ❌ 缺 |
| 6 | **灵感已存卡** | `inspiration_saved` | 一条轻量提示 + 标题 + 标签，点进灵感详情 | 已有 |
| 7 | **电脑操作进度** | `job_update` | AI 正在操作电脑时的进度。手机上只读展示 + 一个 `■ 紧急停止` | 已有（停止按钮缺，二期） |

**另外两条不是卡片但会影响这一屏**

- **`chat_message` 跨端同镜**：在 PC 上发的消息会实时广播到手机（服务端排除发起端）。设计上要知道"消息可能不是我在这台机器上发的却出现了"，所以气泡不要依赖任何本地状态才能渲染。iOS 已支持。
- **`history_cleared`**：另一端点了"清空聊天"，本端要就地清空并给一句轻提示。iOS ❌ 缺 —— 现在会出现"电脑上清空了、手机上还留着一屏历史，下拉刷新才消失"。

**问答卡（必须新做）**

服务端形状（已验证）：

```json
{"type":"question_card","card_id":"q-1","conversation":"assistant",
 "title":"关于这个棋牌小程序，我需要先确认几件事",
 "questions":[
   {"id":"platform","text":"做在哪个平台？","multi":false,
    "options":["微信小程序","支付宝小程序"],"allow_custom":true,"optional":false}
 ]}
```

设计要求：

- 一张卡里可能有**多题**，一次性提交。PC 端做成"一次显示一题 + `上一题` / `下一题` + 最后一题变 `提交`"，手机屏幕更窄，这个分页式反而比长滚动好，**建议沿用**
- 顶部显示进度（`2 / 4`）
- `multi: true` 的题要标 `可多选`
- `allow_custom: true` 的题末尾加一项 `其它（自己写）`，选中后展开输入框，占位符 `在这里作答`
- `optional: false` 的题没答完不能提交（`提交` 按钮置灰，且要说明为什么灰）
- 提交后整卡就地变成 `已提交，秘书这就去安排`，选项不可再改
- **另一端已经答过**：服务端会广播 `question_resolved`，这张卡要自动变成已完成态。设计要有这个状态
- **重连补发**：服务端在握手时会把所有未答的卡重发一遍，客户端按 `card_id` 去重。设计上不用管，但要知道同一张卡可能到达两次
- 客户端提交发 `{"type":"question_answer","card_id":"...","answers":{...}}`

**模式选择器**

`模式`：`自动` / `聊天` / `执行`。PC 端是输入框上方一个小段控件。手机上建议做成输入框左侧一个小胶囊按钮，点开一个 action sheet —— 竖屏宽度金贵，不值得常驻一整行。

**`⋯` 菜单**

`新会话` · `清空聊天` · `复制聊天`。清空要二次确认：`确认清空与秘书的聊天历史？此操作不可撤销（设备会话不受影响）。`

**iOS 特有**：语音输入（长按发送键说话）、`自动朗读回复` 开关（已有 TTS）。

### 3.3 聊天 · 与设备对话 ｜ 一期

**职责**：直接吩咐某台设备做事。秘书仍在中间转译，但任务明确派给这台机器。

**与秘书对话的差别**

- 输入框占位符：`对「{{name}}」说点什么，Enter 发送`
- 空态：`直接吩咐「{{name}}」做事，秘书会把任务派给这台设备`
- **离线横幅**：设备离线时顶部一条黄色横幅 `这台设备当前离线，端侧任务无法执行`
- 导航栏右侧是 `设备详情` 入口（不是 `⋯`）
- 清空确认文案不同：`确认清空「{{name}}」设备会话的记录？此操作不可撤销。`

---

### 3.4 设备详情 ｜ 一期

**职责**：这台设备是什么、在不在线、能干什么。

**数据源**：`GET /devices/all`（含离线的历史设备）、`GET /capabilities`

**布局**

1. 头部：设备头像 + 设备名 + 在线徽标（`在线` / `离线` + `最后在线 {{time}}`）

### 3.5 提醒 · 列表 ｜ 一期 · 待服务端

**职责**：到点叫住我。**这是这一版新增的核心功能**，服务端接口尚未实现，设计已定在 `doc/提醒与定时任务-设计与待办.md`。

**关键设计约束（已在那份文档里拍板，设计要照着来）**

- **服务端是唯一真相源**。推送只是敲门砖，不是数据通道 —— 每次 App 前台化都要主动拉一次"该弹但还没确认的"。所以列表下拉刷新不是可选项，是机制的一部分

**布局**

1. 大标题「提醒」+ 右上 `＋`
2. 分段控件：`待办` | `已完成`

4. 提醒行

   - 主行：提醒文本（最多两行）
   - 副行：时间（`今天 15:30` / `明天 09:00` / `7月28日 14:00`）+ 重复徽标（`每天` / `每周一` / `工作日`）
   - 过期的行：时间用红色 + 一个 `已过期` 徽标
5. 空态：`还没有提醒。在聊天里跟秘书说「提醒我明天 10 点开会」就能建一条，也可以点右上角手动加。`

**交互**

- 点勾选圈 → 完成（有 3 秒 `撤销` 的 toast）
- 点行 → 详情
- 左滑 → `再等 10 分钟` / `删除`
- 右滑 → `完成`
- 下拉刷新（机制必需，见上）

**新建/编辑提醒（一期）**

字段：提醒内容（多行文本，必填）· 时间（日期 + 时间选择器）· 重复（不重复 / 每天 / 每周 / 每月 / 工作日 / 自定义）· 提前提醒（无 / 5 分钟 / 15 分钟 / 1 小时 / 1 天）· 备注（可选）

底部提示：`提醒会推到你所有的端上。电脑关着也不会漏 —— 下次打开时会补上。`

**提醒详情（一期）** —— 这是推送点开的落地页，要能独立看懂

提醒内容（大字）· 时间 · 重复规则 · 备注 · 来源（`聊天` / `手动添加`）· 创建时间 · 底部两个按钮 `完成` / `再等 10 分钟` + 一个 `编辑`

### 3.11 我 · 常用语 ｜ 一期

**职责**：把常写的话存成短语。PC 端在快捷入口里一键粘贴；iOS 上主要是**编辑和复制**。

**数据源**：`GET /phrases`、`POST /phrases/sync`

**同步机制（设计要理解，因为它决定了 UI）**

服务端的实现是**按条目合并 + 删除墓碑**，一次往返完成双向同步：客户端推全量（含本地墓碑）→ 服务端逐条 last-write-wins 合并 → 回全量 → 客户端整份落地。没有 rev、没有冲突弹窗。

**所以 UI 上不需要任何冲突处理界面**，只需要：

- 一个 `立即同步` 按钮
- 一行同步状态，五种文案：`刚刚同步` / `{{n}} 分钟前同步` / `同步中…` / `同步失败：{{err}}` / `尚未同步`
- 没配服务器时：`未配置服务器，仅本机`

**布局**：列表，每行 名称 + 关键词徽标 + 内容预览（单行省略）。计数 `{{n}} 条`。

**交互**：点行编辑 · 长按拖动调序 · 左滑删除 · 点内容区一下复制（`已复制` toast）· 右上 `＋`

**必须显示的安全提示**（照抄 PC 端）：`内容为明文存储，密钥类请放密码保险箱`。常用语没有主密码这一层，服务端能看到内容。

## 四、不在 iOS 做的桌面能力

这一章是给设计看的**边界说明**：这些东西在 PC 端存在，但 iOS 上不做，理由和替代做法都写清楚，设计不用来回问。

| PC 功能 | iOS 不做的理由 | 手机上的替代 |
|---|---|---|
| **快捷入口**（类 Alfred 的全局搜索面板） | 它的整个前提是"按一个全局快捷键、在任何应用之上唤起一个搜索框"。iOS 没有全局快捷键，也不允许应用悬浮在其它应用之上 | 无需替代。iOS 有系统级的 Spotlight，语义重叠 |
| **剪贴板历史** | 需要一个常驻后台进程持续监听剪贴板。iOS 的后台执行模型不允许，应用一进后台就被冻结 —— 只能拿到"打开应用那一刻"的剪贴板，攒不出历史 | 无需替代。真要用，`常用语` 覆盖了"常写的话"这个主要场景 |
| **截图 + 标注 + 贴图钉桌面 + OCR** | 截屏是系统能力（电源键+音量），标注 iOS 自带的"标记"就有，"钉在桌面"这个概念在 iOS 上不成立 | 走系统能力。二期可以做**分享扩展**：从系统截图分享给 Umbra → 存成灵感或发给秘书 |
| **工作流编排（画布）** | 一张有节点、连线、缩放、拖拽、多选框选的图。在 5.5 英寸竖屏上编辑这个不是"难用"，是"做不了" | **只读 + 触发**：二期可以做一个工作流列表，看名字/描述/启停状态，点一下 `在这台设备上跑一次`。编辑一律去 PC。⚠️ 这一项有前置依赖 —— 工作流目前只存在 PC 本地，服务端看不见。要让手机列出来并触发，先得把 PC 的工作流登记成设备能力（provider/skill），设计与待办见 `doc/工作流作为设备能力-设计与待办.md`，那件事没做之前这一项做不了 |
| **实时操作** | AI 正在操作电脑时的实况画面与动作历史。它的价值是"你在旁边盯着，随时按紧急停止"—— 那时你就在电脑前 | 可以做一个降级版：任务详情里如果有 operate 步骤，显示动作历史（只读）。**紧急停止按钮值得做**（`■ 紧急停止`），因为"人不在电脑前发现 AI 在乱点"恰恰是手机能救的场景。列为二期 |
| **日志页** | 纯排障，长文本滚动，手机上读不了 | 塞在设备详情的三级页里，够了 |
| **电脑操作授权 / 权限开关**（辅助功能、屏幕录制、computer-use） | 这些是**执行设备**的系统授权。iPhone 不是执行设备 | 改成**只读展示某台 PC 的授权状态**，放设备详情里。要改去 PC 改。**现有 Me 里的这两个开关要删掉** |
| **全局快捷键总览** | 同上，iOS 无全局快捷键概念 | 不做 |
| **开机自启 / 菜单栏图标** | 平台概念不存在 | 不做 |

## 五、iOS 特有的能力（PC 没有，设计要一并考虑）

这些不是"补齐 PC"，是手机端能做得**比 PC 更好**的事。

| 能力 | 用来做什么 | 分期 |
|---|---|---|
| **推送通知** | 提醒到点、任务完成/失败、有问答卡等你答。带动作按钮：提醒的 `完成` / `再等 10 分钟`；任务的 `查看` | 一期（提醒）· 二期（其余） |
| **通知深链** | 点通知直接进对应详情页（`umbra://reminder/<id>` 这类），不是打开首页让人自己找 | 一期 |
| **Face ID / Touch ID** | 保险箱解锁。这是手机比 PC 体验好的典型 —— PC 上要敲主密码 | 一期 |
| **分享扩展** | 从任意 App 分享文字/链接/图片 → 存成灵感，或发给秘书 | 二期 |
| **语音输入** | 长按发送键说话。手机上打字慢，"提醒我明天十点开会"说比打快 | 二期 |
| **锁屏 / 主屏 Widget** | 今天的提醒、进行中的任务数 | 三期 |
| **实时活动（动态岛）** | 长任务的进度。任务跑二十分钟，手机上能一直看着进度是很爽的 | 三期 |
| **Siri 快捷指令** | "嘿 Siri，让 Umbra 记个灵感" | 三期 |

## 六、跨端一致性清单

这些东西**两端必须字面一致**。不一致的后果是用户在手机上看到"待确认"、在电脑上看到"执行中"，然后开始怀疑数据。

1. **任务状态词与状态色**：见 3.6 的表。包括那条 `agent_state=idle` → 显示成 `待确认` 的特殊规则
2. **灵感状态词**：`待办` / `已实现` / `归档`
3. **灵感来源词**：`手动添加` / `聊天` / `快捷键` / `手机端` / `未知来源`
4. **连接状态词**：`已连接` / `连接中…` / `未连接`
5. **四色语义**：绿=成功、橙=进行中、黄=要人处理、红=失败。**不要在 iOS 上引入第五种语义色**
6. **时间格式**：`昨天 {{time}}` / `{{month}}月{{day}}日 {{time}}` / `{{year}}年{{month}}月{{day}}日 {{time}}`
7. **所有确认弹窗的文案**：照抄，不要自己重写一遍。PC 端那些文案是反复改过的（比如删除工作区要分"仅从列表移除"和"连同文件删除"两种，措辞的严厉程度不同）
8. **保险箱的密钥派生**：主密码派生必须是 PBKDF2-SHA256，参数和 PC 端一致 —— 这不是文案问题，参数不一致会导致 iOS 解不开 PC 存的密文

### 7.2 排版

PC 端用的是 10.5 / 11 / 11.5 / 12 / 12.5 / 13.5 / 14pt 这一套偏小的字号（桌面视距远、信息密度高）。**iOS 上要整体上调**：

| 用途 | iOS 建议 | PC 对应 |
|---|---|---|
| 大标题 | 28pt Bold（大标题栏） | — |
| 区块标题 | 17pt Semibold | 14pt 600 |
| 列表行主文 | 16pt Regular | 12.5pt |
| 列表行副文 | 13pt Regular | 10.5–11pt |
| 分组小标题 | 12pt Semibold + .06em 字距 + `faint` | 10.5pt |
| 徽标 | 11pt Semibold | 10.5pt |
| 等宽（路径、设备 ID、画像） | SF Mono 13pt | 12pt |

**要支持 Dynamic Type**（至少到 XL），别把字号写死。

### 7.3 间距与触达

- 页面左右边距 16pt
- 列表行最小高度 44pt（Apple 的触达底线），带两行副文的行 68–76pt
- 卡片圆角 12pt，列表行圆角 10pt，胶囊/徽标圆角全圆
- 图标块 24pt（列表行内）/ 34pt（表单内）/ 48pt（联系人头像）
- 尊重安全区：底部操作条要在 home indicator 之上，吸底的输入框要跟随键盘

### 7.4 图标

**一律线性 outline，不用彩色 emoji。** PC 端为此专门返工过：emoji 在不同系统上字形和基线对不齐，一列图标看起来歪歪扭扭。SF Symbols 直接用，字重跟文字走。

### 7.5 空态、加载态、错误态

三种要分清，PC 端的教训是"一个 `暂无数据` 打天下"会让用户搞不清是没数据还是没加载出来：

- **加载中**：`加载任务中…` / `加载灵感中…`，用骨架屏或居中 spinner
- **真的没有**：`暂无任务`，配一句引导 + 一个主按钮（比如灵感的 `记一条灵感`）
- **筛选/搜索为空**：`没有匹配「{{q}}」的任务` / `这个筛选下暂无任务` —— 要能看出"清掉筛选就有了"
- **出错**：错误文案 + 一个 `重试`。不要吞掉错误

## 九、给设计的几个提醒

1. **文案照抄，不要重写。** 本文里所有中文都是 PC 端代码里的实际字符串。它们大多改过好几轮（比如任务重试那句 `从失败的那一步继续，已完成的里程碑不重做`，是为了让人敢点那个按钮才加的）。两端文案分叉是很难发现、也很难收回的债。
2. **诚实的脚注要留着。** PC 端有几处专门写了"这个我们做不到"的说明，比如验收清单下面那句 `这里只列标准本身，逐条通过与否服务端没有记录。`。这类脚注看起来像是在自曝短处，实际是在防止用户误解界面。别当成冗余删掉。
3. **状态要分得比你以为的更细。** 任务有七种状态、灵感有三种、连接有三种、同步有五种文案。手机屏幕小容易想合并，但合并之后用户就没法判断"我该做什么"了 —— `待确认` 和 `执行中` 长得一样的话，那个需要他点一下才能继续的任务就永远卡着。
4. **提醒那一块请先读 `doc/提醒与定时任务-设计与待办.md`。** 里面有四条查证过的技术事实（Electron 通知不能定时、`setTimeout` 跨休眠不可靠、APNs 是 best-effort、要靠前台化补拉），它们直接决定了"为什么提醒列表必须有下拉刷新"、"为什么通知里要写那句免责说明"。不读那份文档，很容易把提醒设计成一个纯本地的闹钟。
